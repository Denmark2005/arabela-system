# Arabela Gown Rental System

This document describes what the system actually does today, based on a direct read of the code. It does not include planned features. Anything half-built, inconsistent, or broken is called out in Section 9.

## 1. Overview

Arabela is a reservation and inventory system for a gown/suit rental shop. It replaced a walk-in / Facebook-message booking process with a website where customers can browse real-time availability, reserve a gown online, pay a security deposit, and pick it up in person.

**Tech stack:**
- **Language / framework:** Python, Django 6.0.3
- **Database:** PostgreSQL (hosted on Supabase) in production; falls back to a local SQLite file automatically if no database environment variables are set, so the app also runs with zero DB setup
- **Hosting:** Render (implied by `gunicorn` as the WSGI server and a proxy-aware settings block), with WhiteNoise serving static files directly from the app
- **Media storage:** Cloudinary for gown photos, payment-proof screenshots, and profile pictures — falls back to local disk if no Cloudinary credentials are set (needed because Render wipes local disk on every restart/redeploy)
- **Authentication:** django-allauth, configured for Google sign-in
- **AI feature:** a chat widget backed by Google's Gemini API (not Anthropic, despite an unused `anthropic` package sitting in requirements — see Section 9)
- **Timezone:** Asia/Manila

## 2. User roles

| Role | How it's set | Access |
|---|---|---|
| **Customer** | Any signed-in Google account with no admin flags | Browse, search, reserve gowns, manage their own reservations/cancellations, upload payment proof, read their own message inbox, edit their display name |
| **Staff** | `UserProfile.role = Staff`, `is_staff = True` | The daily work in the admin panel: add/edit gowns, New Booking (walk-ins), approve/reject new bookings, pick-ups and returns, receipts, reminders. **Not** the Manager-only actions below, Staff Management, Categories, tag colors, shop settings or the owner's account-settings page |
| **Manager** | `UserProfile.role = Manager`, `is_staff = True` | Everything Staff can do, **plus** the Manager-only actions: delete gowns (one or in bulk), cancel a confirmed booking or some of its gowns, flag/unflag a customer and remove a cancellation lock, delete a receipt photo. **Not** Staff Management, Categories, tag colors or shop settings |
| **Owner** | `is_superuser = True`, or `UserProfile.role = Owner` | Everything Manager can do, **plus** Staff Management (create/edit/deactivate/delete staff accounts), Categories, tag colors, the shop settings and the owner-only change-password page |

The owner picks the role when creating or editing an account (Staff Management) and the access follows automatically — there are no per-person switches. The Manager-only actions are enforced on the server (`accounts/roles.py` `can_manage()`, used by `arabela_admin.views._manager_error`, which answers 403 "Only a Manager or the owner can do that."), and the same rule hides the buttons from Staff (`admin_can_manage` in the admin context processor). What each person did stays on record: the Removal Log names who removed a gown, each receipt names who uploaded it (also shown in the proof windows), and a deleted receipt leaves a staff-only history line.

Notes:
- A signed-in admin/staff account with no `UserProfile` row at all is treated as **Owner by default** in a couple of places (the header and notifications context processors), which is a looser default than the explicit `_is_owner()` permission check used to actually gate actions — see Section 9.
- **The shop's public phone, Facebook link and address are the owner's alone to change** (2026-11-08). They live in `SiteSettings` and are shown to customers (footer, Contact page). On the admin **Edit Profile** page the "Phone" box in Edit Personal Information is the SHOP's number, not the staff member's own, so Staff and Managers no longer see it (or the Facebook / address editors) at all, and their Save sends only name, email and bio. The page decides with `can_edit_shop_settings` = `_is_owner(request)`, the same check `save_profile_view` makes before it writes those fields, so a box is never shown that the server would silently drop. Tests: `arabela_admin/test_shop_settings_owner_only.py`.
- Customers never see the admin panel at all; there's no in-between "customer with extra permissions" tier.

## 3. Features by module

### Customer-facing site
- **Homepage & info pages** — About, How It Works, Contact, Terms & Conditions, FAQs (static content pages).
- **Collections / catalog** — 13 fixed categories (Wedding Gown, Evening Gown, Long Gown, Luxury Gown, Mother Gown, Suit, Filipiniana, Guest Gown, Dresses, Kids Gown, Barong, Ball Gown Tulle, Bridesmaid Dresses), plus an "All" tab that shows every category together. Multiple physical units of the same gown are shown as one product card with an "available count," not one card per unit. Each category tile shows a picture of a gown on the shop's grey, which the owner manages in Admin → Categories (Section 12).
- **Product detail page** — photo, price, size, an availability calendar (dates a customer can't pick are greyed out), and a "You may also like" section (other real products from the same category — a plain, non-AI recommendation, separate from the chatbot below).
- **Site-wide search** — a search overlay that filters a small in-memory catalog by gown name only (not category or price) as the customer types; shows photo, name, and price per result. Its **View all** button (or Enter) opens a results page, `/search/?q=…`, with every matching gown from every category in one list, sorted Best Match by default.
- **"Arabela Recommends" AI chatbot** — a floating chat widget powered by Google Gemini, answering questions about the shop, policies, and (in theory) the catalog. It is grounded by a hand-written prompt describing shop hours, address, rental steps, and cancellation-lockout rules accurately — but its description of the actual gown catalog is out of date (Section 9).
- **Cart** — stored in the browser's `localStorage`; best-effort mirrored to the customer's account (server-side) so it can be picked up on another device, but the server copy is never treated as the source of truth for price or availability.
- **Reservation hold** — starting checkout begins a 20-minute countdown (tracked server-side in the session, not editable by the customer) that reserves the customer's spot in line while they fill out the form.
- **Checkout** — collects contact details and a required GCash payment-proof screenshot. All prices and availability are re-checked on the server at submission time; nothing from the browser is trusted.
- **The selection ("bag") keeps one row per gown.** The same gown + size + dates is ONE row; "more than one" is its quantity, capped at how many units exist in that size -- and a bag never holds more of a gown than exists, whatever the dates (checkout gives every submitted gown its own physical unit). The rules live in one pure script, `static/js/cart-lines.js` (`window.arabelaCartLines`: `sameLine`, `heldOf`, `tidy`, `overbooked`), used by the gown page's **Book Now** (pressing it again on the same choice just opens the selection; another date for a gown that exists once shows an "Already in your selection" dialog), the drawer and the selection page (they merge duplicate rows left by older taps and save the repaired bag, which also fixes the copy synced to the account), and both **Proceed to Reservation** buttons (refused with a plain message if the bag holds more of a gown than exists). Why: tapping Book Now, going Back and tapping it again stacked identical rows (Wedding Gown 5 six times), and checkout refused the extra ones at the very last step with "no longer available". Checkout also sends **one submitted item per unit of quantity** (it used to charge for a quantity of 2 but book one gown), and when one request names the same gown more often than it exists, the server answers "<gown> is in your selection N times, but there aren't N of it free ... remove the extra ones" instead of blaming the date. Tests: `gowns/test_bag_rows.py` (runs the script for real in Node when Node is installed).
- **Sizes: the full row on the gown page, and "Select size" in the bag.** The gown page always draws **S, M, L, XL, XXL** (Free Size only when the gown comes in it); only the sizes staff really have in Gown Catalog (a unit that is not Out-of-Stock) can be chosen, the rest are faded and dashed with a note on tap (a line-through still means "rented on your dates"). The list of *offered* sizes is unchanged (`size_options`; the page draws `size_choices` from `_size_choices` in `gowns/views.py`). The **+** button on a card now adds ANY gown to the bag: a gown with one size gets it filled in, a gown with several is added with no size and its bag row says **Select size** (like **Select rental date**). One shared rule, `arabelaNeedsSize` in `static/js/reservation-flow.js` (several sizes and none chosen), drives the drawer row, the selection page, both Proceed buttons (a popup -- "This gown needs a size", or "a size and a rental date" -- with **Select size** / **Not now**) and the checkout page, which holds Confirm back like it does for dates. The sizes come from the search catalog every page carries; the checkout page hides the search overlay, so it carries its own small list (`#gown-sizes-data`, context key `gown_sizes`). The server still refuses a several-size gown with no size. Tests: `gowns/test_size_choices.py`, `gowns/test_needs_size.py` (runs the real script in Node).
- **Extra Small (XS) -- Kids Gown only (2026-10-19).** `Gown.Size.EXTRA_SMALL` ("Extra Small", code XS, first in `SIZE_CODES`; migration `gowns/0026_extra_small_size`, choices only -- run plain `migrate` on live). Only ONE category may have it (`EXTRA_SMALL_CATEGORY` = Kids Gown in `gowns/models.py`), enforced three ways: the admin's Add/Edit Gown size list shows "Extra Small (XS) - Kids Gown only" only while the category is Kids Gown (hidden + disabled otherwise, and switching the category away resets a picked XS to Medium), `_validate_gown_fields` refuses it for any other category (including owner-added ones, on Add AND Edit, so an XS kids gown cannot be moved to another category either), and the gown page's size row only ever draws an XS button for a Kids Gown. A Kids Gown page draws XS S M L XL (XS greyed until staff add one, like every missing size; no greyed XXL -- a kids XXL still shows if staff ever gave one); every other category is unchanged (S M L XL XXL). XS books like any size (`_SIZE_ALIASES` accepts XS / Extra Small, the bag/checkout script `arabelaSizeCode` knows it, the booking records "Extra Small"), and the Kids Size Guide's first row (3-4 Years) is now highlighted for a real XS button. Tests: `gowns/test_xs_size.py`.
- **Size Guide (Suit, Wedding Gown, Filipiniana, Dresses, Barong, Mother Gown, Guest Gown, Evening Gown, Luxury Gown, Long Gown, Bridesmaid Dresses, Ball Gown Tulle, Kids Gown -- 2026-10-18/19; only owner-added categories have none).** The gown page's "Size Guide" link used to sit on every gown and do nothing; it now shows only where a guide exists. The tables are plain data in `gowns/size_guides.py` (`SIZE_GUIDES`, keyed by the category name as the shop writes it): S to XXL in cm and inches exactly as the owner's charts print them -- Suit: chest/bust, shoulder width, sleeve length, waist; Wedding Gown, Filipiniana and Dresses: bust, waist, hips (the owner gave the same numbers; each category keeps its own copy via `_bust_waist_hips_guide`); Mother Gown, Guest Gown, Evening Gown, Luxury Gown, Long Gown, Bridesmaid Dresses and Ball Gown Tulle: bust, waist, hips with their own numbers and only four rows, S to XL (no XXL; the owner's Evening, Luxury, Long, Bridesmaid and Ball Gown Tulle charts print inches first, they are shown cm first like the rest; those five currently carry the same numbers but each keeps its own copy); **Kids Gown is by AGE**: a first column of age brackets (3-4 Years ... 11-12 Years), then the size tag, chest/bust, waist and approximate length (shoulder to hem), each in cm and inches; its first row (3-4 Years, size XS) is a size the shop does not make, so it is shown but never highlighted, and S/M/L/XL are 5-6/7-8/9-10/11-12 Years as the owner's chart says (`AGE_BANDS` in `add_kids_gowns.py` now says the same); a guide may give its own `first_heading`, row `label`s and `headings`, which is all Kids Gown needs; Barong: chest/bust, shoulder width, sleeve length, length (a category's columns are its own; the page adds "(cm / in)" to each heading). To give another category a guide, add its entry there -- the page and the tests follow it. A gown in Free Size only gets no guide. The panel is deliberately ONLY the table (the owner rejected a first version with a title, "Not available" tags, a how-to-measure block and a footer as over-designed, then a dark version because the dark was only their reference screenshot's colour): a WHITE panel in the customer site's own look -- Poppins, small uppercase labels like "SELECT SIZE", dark centimetres, grey inches (`#615e57`), thin light row lines, headings like `CHEST / BUST (CM / IN)`; every size is drawn the same whether or not that suit comes in it; nothing scrolls (the panel's scrollbar is hidden, there is no scrolling wrapper -- an `overflow-x` wrapper plus the old row slide-in once made a scrollbar flash in while it opened) and nothing slides (the panel and backdrop just fade in, with a tiny rise). `templates/products.html` draws it (`.sg-*` styles; one line per cell on a wide desktop, cm over inches below 960px) and `static/js/size-guide.js` runs it: the row of the size chosen on the page gets a light grey background and a dark left edge (the script only reads the page's size buttons), and Esc, the X or a tap outside close it. No database change. Tests: `gowns/test_size_guide.py`.
- **My Reservations** — order history, a detail page per gown with its own timeline, a cancel button (with rules), and payment-proof upload for reservations still awaiting review.
- **Messages inbox** — in-app notices from staff/system: account flagged/unflagged, pick-up/return reminders, overdue notices, cancellation-lockout warnings.
- **Profile** — a customer edits their display name and keeps up to 5 saved addresses (one can be the default). The addresses are saved on the account (`accounts.SavedAddress`), so they follow the customer to any phone or laptop; the checkout's address boxes start from the default one.

### Admin panel
- **Dashboard** — live counts (registered customers, active rentals, total/available/out-of-stock gowns, reservations this month) that always match the detail page they link to; also the trigger point for the daily reminder sweep (see Section 5).
- **Rental Schedule (calendar)** — a calendar view of every booking's current stage (Pick-up, Reserved, Return, Overdue).
- **Pending Approval** — queue of reservations awaiting a first staff decision.
- **Payment Verification** — approve or reject a reservation based on its uploaded GCash proof.
- **Active Reservations** — rentals that are still running (waiting for pick-up, out with the customer, or overdue); a booking leaves the list the moment its last gown is returned. The colour key at the top is a filter (**All / Confirmed / Active / Overdue**, with counts); late bookings come first and say how many days late they are. Staff can mark a gown returned, change the pick-up date (earlier, and — after an earlier move — back up to the day the customer originally booked, never later and never onto another booking's days; the days a move back gives up are free for other customers at once) or the return date (later only), undo an accidental pick-up, or send a manual reminder.
- **Reservation Records** — a per-reservation ledger, including searching for a reservation to manually attach a photographed paper receipt. **View** opens a calmer booking-details window (one scroll, larger type, no sideways scroll): a pinned header (name, booking code, status, small chips for "Booked under the name" / how a walk-in came in), the notices (payment missing, cancellation facts), the three facts staff look up most (rental period with its day count, total, deposit status), Contact with Copy buttons, ONE CARD PER GOWN with a Pick-up → Event → Return line and the actual pick-up / return dates, Payment, Manual Receipts (Upload Receipt turns solid blue only while a payment is still missing) and History (latest 3 with "Show all N updates", no scrollbar of its own). It is the same data and the same actions as before; all its styles are `rrd-` rules in `reservation-records.html`, so the History list the other pages share is untouched.
- **Rental History** — every gown that went out, one row per gown (Completed / Ongoing / Overdue / Not picked up) with how many days late it was or is, counted from the return date the customer booked. Linked under Bookings & Schedule, right below Active Reservations.
- **Security Deposits** — which reservations are still holding a deposit, and a one-click "release deposit" action.
- **Gown Catalog (Inventory)** — add/edit/delete gowns one physical unit at a time, bulk actions, photo upload, status changes, and "Blocked Dates" (temporarily pulling one unit out of the bookable pool for cleaning/repair/alteration/other reasons).
- **Categories** *(Owner only)* — the picture each category shows on the customer site (Rentals page, Women's and Men's pages, home page): upload, replace, or go back to the standard picture (Section 12).
- **Clients** — the customer list, with a flag/unflag action for accounts under review.
- **Staff Management** *(Owner only)* — create, edit, deactivate, or delete staff/manager accounts.
- **Account Settings** *(Owner only)* — change the owner's own login password.
- **Notifications** — a header dropdown of live work items (pending approvals, unverified payments, overdue returns, late pick-ups, deposits still held, out-of-stock gowns, flagged customers, and, for the owner, deactivated staff accounts). Nothing here is stored — it's recalculated from real data (on every page load, and again every ~15 seconds while an admin page is open, through a small JSON feed at `api/notifications/`), so it can never fall out of sync, but that also means there's no history of past notifications. While a page is open the bell updates by itself and announces anything new with a chime, a toast, the tab title and (opt-in) a desktop pop-up; what each person has already seen is remembered only in their own browser.

## 4. Gown data

Every gown is one row (one physical unit) with these fields:

| Field | What it stores |
|---|---|
| `gown_id` | Unique ID, auto-generated as `CATEGORY-COLORCODE-###` |
| `name` | Product name |
| `slug` | Auto-generated, unique, URL-safe version of the name |
| `category` | One of 13 fixed choices (listed above) |
| `color_name` / `color_code` | Free text — not locked to a fixed list, so an "Other" color can always be entered. A list of 36 named presets (e.g. White/WH, Blush/BL, Royal Blue/RB) drives the Add/Edit dropdown and warns staff if a code is already used by a different color name. |
| `size` | Extra Small (shown as **XS**, Kids Gown only), Small, Medium, Large, Extra Large, Extra Extra Large (shown as **XXL**), or Free Size |
| `design_variant` | Optional free-text note (e.g. a style variant) |
| `rental_price` | Decimal peso amount |
| `condition` | New, Good, Fair, or Needs Repair |
| `status` | Available, Reserved, or Out-of-Stock (there is no "In Cleaning" or "Lost" status — see Section 6) |
| `photo_url` | Link to the gown's photo |
| `is_verified` | Yes/no flag |
| `last_returned_at` | Date it was last returned, if any |
| `notes` | Free-text staff notes |
| `created_at` / `updated_at` | Automatic timestamps |

**How names/IDs are created:** `gown_id` and the URL slug are both generated automatically using a counter that takes a database row lock before handing out the next number — this was specifically built to survive two staff members adding a gown in the same category/color at the exact same moment without colliding. **Renumbering the Wedding Gowns (`reset_wedding_gowns`, one-off, 2026-10-17):** the shop's wedding gowns were named after their photos (Wedding Gown 01-33) and numbers 18, 19, 21, 22, 23 never existed, so the owner asked for 28 gowns in a row: Wedding Gown 1-28, IDs `Wedding Gown-WH-001`..`028` (photo 20 -> 18, 24 -> 19 ... 33 -> 28), all White, the owner's prices, and the next gown added gets 029. It changes only each gown's name, ID, colour, price and the category counter (plus the name on booking lines that point at the gown); the gown row, photo, slug (web address), size, status, bookings and blocks stay. It refuses unless the category is EXACTLY the 28 described gowns (each old number once), runs as one atomic step, uses a temporary-ID step so IDs never collide, and says so when already done. Take a backup, then `python live.py reset_wedding_gowns --dry-run` and `python live.py reset_wedding_gowns`. Tests: `gowns/test_reset_wedding_gowns.py`.

## 5. Rental flow

1. Customer browses a collection or searches, opens a product page, and checks the availability calendar.
2. Adds it to their cart (stored in the browser).
3. Starts checkout — this begins a 20-minute hold on their spot.
4. Fills in contact details and uploads a GCash payment-proof screenshot, then submits.
5. The server re-checks availability and price from scratch (never trusting anything sent by the browser), locks and assigns one specific physical gown unit, and creates the reservation with status **Pending**. The security deposit is a fixed ₱2,000 per gown. The customer picks an **event date**; the server works out the real pick-up day itself (see the event-date rules below) and an automatic 5-day "Cooldown" block is placed on that gown right after the return date.
6. A staff member reviews the payment proof and approves (**Confirmed**) or rejects (**Rejected**) the reservation.
7. The system automatically sends in-app reminder messages: pick-up tomorrow/today, return tomorrow/today, and an overdue notice (capped at 30 days of nagging). These run once a day, triggered the next time any staff member opens the dashboard — there is no real scheduler/cron behind this.
8. Staff track the gown's real-world stage on the Rental Schedule calendar or Active Reservations: **Pick-up → Reserved → Return**. **Overdue is worked out automatically**: a gown that is out and past its return date shows as Overdue (with the days late, counted from the return date the customer booked) on Active Reservations, the Rental Schedule and Rental History, and the automatic reminder message above goes out too.
9. When the gown comes back, staff mark it returned as either **Good** or **Needs Repair**. Needs Repair takes the physical gown out of the bookable pool (Out-of-Stock); Good keeps it available once its cooldown period passes.
10. **Cooldown:** every booking automatically blocks its gown for 5 extra days (`COOLDOWN_DAYS` in `gowns/models.py`) right after the return date, which is itself 2 days after the event. So the gown is off the market for **7 days after the event**: 2 days to bring it back, then 5 days to check, wash and repair it. Example: event Oct 20, return Oct 21–22, cooldown Oct 23–27, so the next customer can pick the gown up on Oct 28 and Oct 28 is already a choosable event date (same-day pick-up). The same number is used at checkout and whenever staff change a return date or mark the gown returned (the 5 days then start from the actual return day). Staff can shorten or delete this block by hand once they've actually checked the gown. Bookings made before this change keep the 3-day block they were created with until their return date changes. **The rest goes away with a booking that never went out:** cancelling an approved booking (`reservations/cancellation.py`) and **rejecting** a Pending one (`reservation_reject_view`) both delete that booking's automatic rest blocks, so the gown is free again for the whole span it held. (Rejecting used to leave the 5 rest days behind, so that size stayed blocked for up to 7 days after the event; other sizes of the same design were never affected, because every size is its own gown with its own rest.) Each size of a design is a separate unit: one size rented on a date leaves the others bookable that same date, and the date only greys out for the whole gown once every size is taken. Tests: `gowns/test_same_gown_other_sizes.py`.
11. Once every gown in a reservation is marked Returned, staff can release the security deposit with one click. **The system only tracks whether the full deposit was released, and when** — it does not calculate or record a partial deduction for a late return or damage. Any late fee (₱200/day is the shop's stated policy) is handled entirely by staff outside the system.
12. A customer can cancel anytime before pick-up, as long as no gown in that reservation has already been picked up. Cancelling — and separately, letting a checkout hold expire or cancelling it — both count against the same limit: 5 strikes = a 30-minute lockout on starting a new reservation, 10 strikes = a 2-hour lockout, 15 strikes = the account is permanently flagged for staff review (only an admin can clear a flag).

**Event-date rules (Philippine time).** One planner, `gowns/availability.py`, decides which event dates can be booked and which day the gown is picked up. The gown page's calendar, checkout (`_plan_pickup` in `gowns/views.py`) and the admin's release reminder all use it, and `gowns/test_event_dates.py` proves the page and checkout agree for every event date and size.

- The customer picks the event date. Return is 2 days after it, then the gown rests 5 days. A rental therefore needs **8 days in a row** to be free (the event day, 2 return days and 5 cleaning days).
- Pick-up is the earliest free day up to 2 days before the event. When those days are taken or blocked, it is the **event day itself**. Pick-up is always **1:00 PM to 5:00 PM only**.
- Today can be chosen until 5:00 PM. From 5:00 PM today is closed ("Today's pick-up closed at 5:00 PM") and the earliest pick-up is tomorrow; an event tomorrow is still allowed, picked up tomorrow.
- The server checks its own clock at submit, so a date that passed (or today after 5:00 PM) is refused with a clear message even if the browser sent it. The bag and the checkout hold are kept so the customer only fixes the date.
- Rest-day protection: a new booking's 5 rest days may never run into a later customer's booking. They may overlap a staff block (the gown is being cleaned anyway). A free gap shorter than 8 days therefore shows greyed out on the calendar.
- When staff release a blocked range in Gown Catalog, a reminder first shows which event dates it would really open for customers. If the free gap around it is shorter than 8 days, it says customers still won't be able to book it (`gown_block_release_preview_view`, `/api/gown-blocks/<id>/release-preview/`).
- The customer sees "Pick-up: <date>, 1:00 PM to 5:00 PM only" on the gown page and the order summary, and in the confirmation email and the pick-up reminders.

**Availability label on gowns.** Every gown list (each collection page, "All" and Search) and the gown page show the SAME label, worked out from the real bookings and dates by `gowns.availability.booking_badge` (the same rule as the calendar and checkout): no label at all while the gown can be booked now (or tomorrow); **"Available from Oct 26"** when the first event date that can be booked is later (that is the first date the calendar offers); **"Fully booked for now"** when nothing in the calendar's 4 months can be booked (the + is greyed out only then); "Currently Unavailable" on the page of a removed gown. It replaced "Limited Availability" / "Available Now", which the card decided from the saved "Reserved" status (still on for a booking a month away, or one never picked up) and the page from the dates, so they could disagree. A page of cards reads the bookings once (`_busy_for`), not once per card.

**Cancel booking (staff).** Active Reservations has a red **Cancel booking** button for an approved booking nobody has picked up (a no-show, or the customer phoned to cancel). It opens a window with the customer, booking code, gowns, event date and the deposit; staff pick a reason and must type the booking code before the red button turns on. Cancelling never deletes anything: the booking becomes **Cancelled**, the customer's timeline gets a "Reservation cancelled by Arabela" entry and staff get a staff-only note with the staff member's name and the reason, the gown goes back to Available unless another live booking needs it, the automatic 5-day rest is removed, and the customer gets an in-app message and an email. It counts toward the customer's cancellation limits like their own cancellations. **The security deposit is not refunded.** Reservation Records has a **Cancelled** card; every cancelled booking (cancelled by the customer or by staff) shows who cancelled it, when, why, and either "Deposit ₱X was paid and verified on <date>. It is not refunded." or "Cancelled before the payment was verified." -- so when a customer phones the shop, staff search the name or booking code and see the deposit was already paid. The admin bell shows ONE entry per late booking (not per gown): a warning once the pick-up date passes, and a red "Cancel booking" entry once the event date has passed. A gown that never left the shop is no longer also reported "overdue for return". No database change: who, when and why are read from the booking's status log (`reservations/cancellation.py`). Not automatic on purpose: staff decide.

**Long lists show 15 rows at a time (admin).** Active Reservations, Rental History, Reservation Records, Gown Catalog, Clients, Pending Approval, Payment Verification and Security Deposits no longer scroll on and on: each shows 15 rows, with **Back / Next**, page numbers (the current page is the filled blue one), "Page 2 / 46" at the top and bottom of the list, and "Showing 16–30 of 685 …". It is ONE script, `static/arabela_admin/pager.js`, that sits on top of each page's own search / filter / sort and changes none of it: a list opts in with `data-arpg="tbody"` (or `data-arpg=".some-class"`) and `data-arpg-noun` on its scroll box, the page's own filter still decides which rows MATCH, and the pager only hides the matching rows that are not on the current page with its own `data-arpg-off` attribute. A booking with several gowns, or an item with its opened Timeline row, always moves as one unit, so nothing is cut across two pages. The page number is kept in the address (`?page=3`), so the reload that follows many admin actions stays on the same page; a new search, filter or sort goes back to page 1; a list of 15 rows or fewer looks exactly as before (no pager). **Clicking through the pages keeps the screen still:** the list box keeps the height of a full page on every page (a last page with fewer rows no longer shortens the card, so the Back / Next bar never jumps up from under the pointer and the page never loses its scrollbar and slides sideways), the height is pinned BEFORE any row is hidden (hiding first would shorten the page for a moment and the browser would scroll it), the page itself is never scrolled by a click (only the list's own scroll goes back to its first row), and past 7 pages the number row is always 7 equal-width slots so Back / Next never slide. If the script ever throws it shows every row again (`failOpen`), i.e. the old behaviour. Gown Catalog: the header tick box ticks the 15 gowns on the page being shown, with a **Select all N matching** button once the page is fully ticked; ticks are kept across pages. This is paging in the browser (every row is still sent to the page); the lists that grow forever (Reservation Records, Rental History, Clients) are the ones to move to paging in the database if they ever reach many thousands of rows.

**Proof of payment is a picture, and only a picture (customer side).** The proof a customer uploads at checkout, on the reservation page and on My Reservations used to be accepted on its file NAME and on the "type" the sender's browser claims, both chosen by the sender: a PDF, a web page or a Windows program renamed `receipt.jpg` (or an empty file) was stored exactly as sent. Now: (1) `gowns/proof_image.py` OPENS the upload as a picture (only JPEG, PNG and WEBP decoders may try; empty, corrupt, over 5 MB or over 25 million pixels is refused) and stores a REBUILT copy under a random name (`<random>.jpg|png|webp`, the customer's file name is never used) — a screenshot stays a PNG so GCash reference numbers stay sharp, a photo stays a JPEG, a phone's rotation is applied and its hidden details (GPS, camera) are dropped, and anything glued behind or inside the picture (a PDF, a script, a program) is not in the copy; `_prepare_proof_upload` in `gowns/views.py` runs it before anything is saved, in both `reservation_submit` and `reservation_upload_proof`. (2) `arabela_system.middleware.ProofUploadSizeGuardMiddleware` answers a proof upload that announces more than 8 MB with 413 before the body is read (it sits before CSRF and the session). (3) `arabelaProofPhotoProblem` in `static/js/picked-file.js` tells the customer right when they pick a PDF, video or other file ("take a screenshot of it and upload that"); a big camera photo is NOT judged until the page has shrunk it (>1.5 MB becomes a 1600 px JPEG), then over 5 MB is refused. The 5 MB limit stays: GCash screenshots and saved receipts are usually well under 1 MB. Tests use the real tiny picture in `gowns/sample_images.py` (fake JPEG bytes are now refused, like a renamed PDF). The staff-side uploads (receipts, gown photos) still use the older name/type check; they are signed-in staff only.

## 6. Inventory tracking

- Each physical gown is tracked as its own database row with its own `gown_id` — this is **not** a "1 product, quantity 5" model under the hood.
- For display, gowns sharing the same name (case-insensitive) are grouped together into one product card, and the cheapest unit in that group is used to represent its price and photo — this is what produces the "1 product, several available" experience customers see.
- There is no separate "stock count" field; the count is simply how many gown rows share that name, computed on the fly.
- **There is no formal inventory audit trail.** A gown's own edits (price changes, condition changes, status changes) are only reflected in its `updated_at` timestamp — there's no log of who changed what on the gown itself (as opposed to reservation actions, which are logged — see Section 7).
- **There is no dedicated "missing" or "lost" status.** The only statuses are Available, Reserved, and Out-of-Stock — a gown that's actually lost or destroyed would have to be represented as Out-of-Stock with an explanation typed into the free-text `notes` field, if a staff member remembers to.
- **Blocked Dates** is the general mechanism for pulling one unit out of the bookable pool for a date range, tagged Cleaning, Repair, Alteration, Cooldown, or Other. Cooldown blocks are created automatically by the system (see Section 5); the rest are added by staff by hand.

## 7. Logs and history

- Every meaningful thing that happens to a reservation — submitted, approved, rejected, cancelled, picked up, stage changed, marked returned, deposit released, reminder sent — is written to an append-only event log, tagged with who did it (Customer / Staff / System) and when. Nothing in this log is ever edited or deleted after the fact.
- Some log entries are marked staff-only (e.g. an internal note that a gown came back needing repair) and are hidden from the customer's own order timeline; the admin panel's timelines always show everything.
- **This logging only covers reservations, not gowns.** There's no equivalent log for inventory changes — no record of who edited a gown's price, condition, or status, or when.
- The admin notification bell is **not** a log either — it's a live list recalculated from current data on every page load and every ~15 seconds after that (see Section 3), so there's no historical record of past notifications, only what's currently outstanding.

## 9. Not built yet / known issues

- **The AI chatbot's product knowledge is stale and wrong.** Its instructions still describe an old placeholder catalog that was retired ("11 collections, each with 8 items named One through Eight," a fixed price ladder, item "Two" always Reserved). The real catalog now has 13 categories with real, staff-entered names and prices. The chatbot was never updated to match, so it will confidently recommend gowns that don't exist.
- **Cash is not actually a selectable payment method**, even though it's a valid choice in the data model and the FAQ/product-page copy tells customers "the system accepts GCash and cash payments." The real checkout form only ever submits GCash — there is no button, dropdown, or any way for a customer to choose Cash.
- **The AI chat silently does nothing useful if its API key isn't set.** With no `GEMINI_API_KEY` configured, every chat message gets a generic "having trouble thinking right now" reply instead of a real answer — and that environment variable isn't even listed in the project's example environment file, so a fresh setup could easily miss it.
- **The AI chat's rate limits aren't reliable in a multi-process deployment.** Its 10-per-minute / 40-per-day limits are enforced using Django's default in-memory cache (no shared cache is configured), so in production each server worker process counts separately, and the daily counter resets on every restart/redeploy instead of at midnight.
- **A fresh database deployment will crash the login page** until someone manually creates a Google-login configuration row through Django's own admin site — this isn't created by any migration or setup script.
- **Classic email/password sign-up is fully configured but unreachable.** The settings require mandatory email verification for it, but there's no sign-up form anywhere on the site — Google sign-in is the only way in. This is effectively dead configuration.
- **Saved addresses are on the account now (they used to be browser-only).** `accounts.SavedAddress` (migration `accounts/0015`, one new table; the database itself allows at most one default per customer through a partial unique index). The profile page saves through `profile/addresses/save/`, `.../<id>/delete/` and `.../import/` (`gowns/views.py`, tests in `gowns/test_saved_addresses.py`); every answer carries the customer's whole list. Rules the server enforces: sign-in required, a customer only ever sees or changes their own, all four boxes required, a 4-digit postal code and an 11-digit phone, at most 5 per customer (the customer's row is locked while they change, so two taps or two devices cannot break the limit or the one-default rule), and a second tap on Save is ignored. **One-time copy-over:** the first time a customer opens their profile after this shipped, an account with no saved addresses takes over the ones that browser kept in localStorage (only into an empty account, so it can never duplicate or overwrite; entries saved under older, looser rules are kept; at most 5, one default; exact repeats dropped). Once tried it is never tried again (a flag in the browser), so deleting every address later cannot bring old ones back, and the browser's old copy is removed when everything was copied. Until a customer has opened the profile once, the checkout still falls back to the browser's old copy. The checkout reads the list the page was sent with (`json_script`), so any phone or laptop has it. Not visible to staff.
- **A leftover comment in the codebase still describes the AI chat widget as "mock replies, no backend"** — that was true at an earlier stage but isn't anymore; it's now a real, working Gemini-backed feature.
- **Security deposit release has no partial-amount tracking.** The system only records whether the full deposit was released and when — any late-fee deduction has to be worked out and handled by staff entirely outside the system.
- **"Overdue" is not automatic.** The system will message a customer automatically once their return is late, but the visible Overdue status on the staff calendar has to be set by hand.
- **No missing/lost gown tracking, and no audit log for inventory edits** — see Section 6.
- Two unused, leftover dependencies sit in the project's requirements: `mssql-django`/`pyodbc` (the project only ever connects to PostgreSQL or SQLite) and `anthropic` (the real AI feature runs entirely on Google Gemini).
- **Customer emails are built but stay off until they are set up** — see Section 10. Until then, every reminder and notice is an in-app message only.
- A separate vendor UI-kit source project (`arabela_admin_panel_template/`) sits in the repository but is not part of the running application at all — it's not installed, not routed, and any "Coming Soon" text inside it does not describe a gap in the real product.
- Minor: the customer profile template file is misspelled `profile.htmls` instead of `.html`. It works correctly, but it's inconsistent with every other template in the project.

## 10. Customer emails

Customers are also emailed about their own booking. The in-app notices (Messages page and reservation timeline) are always still there; the email is an extra.

| Email | When it is sent |
| --- | --- |
| We received your reservation | right after checkout |
| Reservation approved / rejected (with the reason) | staff approve or reject it |
| Pick-up and return reminders, overdue notice | the daily reminder sweep, and a reminder staff send by hand |
| Security deposit settled | the last gown on the booking is checked back in |
| Account flagged / unflagged | staff flag or unflag it, or the automatic flag at 15 attempts |

Not emailed on purpose: the temporary-lock notice, the "lock removed" message, check-ins (picked up / returned), date changes, and anything the customer did themselves (cancelling).

**How it works** (`accounts/customer_emails.py`): hooks on the two places notices already come from (`CustomerMessage` and `ReservationStatusEvent`), so no existing screen was rewritten. An email is sent only after the database transaction commits, by one background thread that never touches the database. Any failure is logged (Render's Logs tab, `accounts.customer_emails`) and swallowed, so an email can never break an approval, a reminder or a timeline entry. Placeholder addresses (`.invalid`, `example.com`, ...) and accounts with no address are never emailed (the owner and staff ARE emailed when they are the one who booked), and a double-clicked Approve sends one email, not two. The look is `templates/emails/email.html` (tables and inline styles, the only thing every mail app agrees on); the logo is attached inside each email, so it shows even while a free Render service is asleep. The shop's address, phone and Facebook link come from Edit Profile.

**Setting it up** (environment variables on Render; no migration):

1. **A way to send.** Render's **Free** plan blocks the normal Gmail connection (SMTP, ports 25/465/587), so pick one:
   - *Paid Render plan:* keep `EMAIL_BACKEND` as is and set `EMAIL_HOST_USER` (the shop's Gmail address) and `EMAIL_HOST_PASSWORD` (a Gmail App Password).
   - *Free — the Google relay:* open `apps_script/mail_relay.gs`, follow the steps at the top of that file (about 5 minutes in the shop's Google account), then set `EMAIL_BACKEND=accounts.email_backends.AppsScriptRelayBackend`, `EMAIL_RELAY_URL` and `EMAIL_RELAY_SECRET`. Emails are then sent by Gmail itself over HTTPS.
2. **Check delivery.** Admin → Edit Profile → *Customer emails* → *Preview and test emails*. It shows the current status and lets the owner preview every email at computer and phone width and press **Send test to me** (it mails the signed-in owner's own address, and works even while the switch below is off). The same page can send a real test to an existing CUSTOMER's address (to prove delivery to a customer's Gmail; a stranger's or a staff address is refused) and keeps an **Email history**: every email the site tries to send is saved (`accounts.CustomerEmailLog`) as sent (accepted by the Google relay), failed with the relay's reason, or not sent with the reason (no address, a placeholder address), with the booking code and the customer's full address (owner-only page; the server logs keep masking it). It shows 25 to a page with Newer/Older, a filter on the result and a search by address or booking code, survives restarts, and rows older than about six months are removed as new ones are written. Saving a row never stops an email, and until the migration (`accounts/0014`) is applied on the live database the page falls back to a short in-memory list and says so. Render's Logs (`accounts.customer_emails`) hold the same lines.
3. **Switch it on, last.** Set `CUSTOMER_EMAILS_ENABLED=true`. It is **off by default** on purpose: local development shares the live database, so approving a real booking from a laptop must never email a real customer.
4. Optional: `SITE_BASE_URL` (for the links and logo in emails). When blank it is taken from the Site row the deployment uses (`SITE_ID=3` on Render, `arabela-gown-rental.onrender.com`).

**Limits:** Gmail allows about 500 emails a day over SMTP (some sources say 100) and the relay about 100 a day on a normal Gmail account; both are far above this shop's volume. Mail from a Gmail address that is not on an owned domain can land in a customer's Spam folder now and then — the owner's test email is the best check.

## 11. Owner account, passwords and recovery

The shop has **one owner account** — the sign-in for this admin panel. Staff and managers sign in with accounts the owner creates in Staff Management.

**Changing the owner's username or password** (owner only; staff cannot): Admin → Edit Profile → **Login & Security**, or the avatar menu → **Account settings**.

- Both forms ask for the **current password**.
- **Username:** 4–30 letters, numbers, `.`, `-` or `_` (at least one letter), unique ignoring capitals across every account. The owner stays signed in.
- **Password:** at least 10 characters, not one of the most common passwords, not only numbers, not close to the username. Changing it signs out every other device. Staff passwords set in Staff Management follow the same rules (existing staff keep theirs until it is reset).
- **Separate sign-ins for the admin panel and the customer site.** A browser keeps one session cookie per web address, so with a single cookie signing in to the admin panel in one tab replaced the customer's sign-in in every other tab (the customer tab "changed account" on refresh, and a booking made in it was saved under the wrong account). `arabela_system.middleware.SplitSessionMiddleware` now keeps the admin area (`/admin-panel/`, `/admin/`) in its own cookie (`sessionid_admin`); the customer site keeps `sessionid`. An admin who was already signed in under the old single cookie stays signed in (a staff session in the old cookie is still honoured in the admin area; an ordinary customer's never is). Related guards: a Google sign-in whose address belongs to a staff/superuser account is refused with a message (it used to be connected to that account, which opened the admin panel without its password); checkout sends the account its page was opened for (`expected_user`) and the server books nothing if the sign-in changed since; the live badge script shows a bar when the account in this browser changed or was signed out in another tab; and a customer email that is skipped is logged as a WARNING with the reason (`Customer email NOT sent: ... the address is a placeholder ...`).
- **Google sign-in errors are friendly.** If Google's answer can't be used -- most often the same answer arriving twice because of a second tap on the account, a refresh, or Chrome on a phone replaying the whole sign-in when "Desktop site" is switched on or off (the first one already signed the person in) -- allauth's bare "Third-Party Login Failure" page is never shown. `ArabelaSocialAccountAdapter.on_authentication_error` sends someone who is already signed in back to where they were headed (the checkout page for a guest who pressed Proceed to Reservation; the homepage when nothing is remembered), and anyone else back to the login page with a plain reason (`?problem=incomplete` or `cancelled`, words taken only from `accounts.views.SIGN_IN_PROBLEMS`) that still carries `next`. Where they were headed is `accounts/login_next.py`: `login_view` remembers the safe `next` path in the session for 15 minutes, and it is only ever followed if it is still a path on this site. The checkout form also remembers what was typed (name, address, city, postal code, phone, GCash reference) in this tab's sessionStorage and puts it back when the page loads, so the reload that repeat answer causes does not empty the form (the receipt photo cannot be kept -- a browser never lets a page re-fill a file); it is dropped once a booking goes through (`gowns/test_checkout_draft.py`). **What each box starts with** is decided by one pure rule, `static/js/checkout-fields.js` (`chooseValue`, run for real in Node by `gowns/test_checkout_fields.py`): the profile's saved default wins over anything remembered from an EARLIER checkout and over what was typed before the default was changed; what the customer typed over a default in THIS checkout survives a reload; with no default for a box, what was typed before comes back. Each remembered value therefore carries the default it was typed against (`{value, base}`); it is only trusted while the profile still says the same for that box. (Before this, remembered values were put back first, so a default saved later never showed.) The two name boxes of the profile's Edit profile window now have `w-full min-w-0` like the address boxes -- without a width of their own the last-name box ran past the window on a phone's wider font or in Desktop mode. The Continue with Google link also ignores a second tap from the first moment the page exists.
- **Previous sign-in** (shown on both pages): when the account signed in before the current session, so a sign-in the owner does not recognise can be noticed. It is kept in the session, so there is no database change.
- 5 wrong sign-in attempts for a username lock that username for 15 minutes (the lockout ends 15 minutes after the 5th wrong attempt, and the message says how many minutes are left). The count is kept in the database (`accounts.LoginThrottle`, migration `accounts/0013`), so an app restart or a refresh cannot reset it; before that migration has run it falls back to the server's memory.

**Forgot password (owner only)** (`accounts/owner_recovery.py`, `arabela_admin/recovery_views.py`; needs migration `accounts/0016_ownerrecovery` -- until it is applied the pages say the update is not ready and nothing else changes). The owner can recover her own password by email; staff and customers never can (a staff member who forgets a password asks the owner, who resets it in Staff Management).

- **Recovery email** -- Account Settings → *Recovery Email*. It is a separate address from the profile's Email box on purpose: anything typed into a profile box without proof must never decide who may reset the admin password. Setting or changing it needs the **current password** (5 wrong tries lock only this card for 15 minutes; it never locks the sign-in page) **and a 6-digit code mailed to the NEW address**. The address is saved only when the code is typed back, so a mistyped or made-up address can never become the recovery address, and the old one stays active until the new one is proven. The code works for 15 minutes, 5 tries, one email every 30 seconds and at most 5 an hour. It is kept only as a keyed hash in the owner's own session (never in plain text, never in a table). Replacing a confirmed address emails the OLD one ("your recovery email was changed", new address masked). Only the masked address (`o***@gmail.com`) is ever shown back in the page.
- **Forgot password?** -- a link on the admin sign-in page (`/admin-panel/forgot-password/`). It asks for the owner's **recovery email** (an Email box; it used to ask for the username, which confused testers) and always shows the same message and does the same work whether or not the address belongs to anyone (the email is sent from a background thread, so the answer is not slower either). The address is matched ONLY against the confirmed recovery emails (`accounts.OwnerRecovery`, case-insensitive) -- never the profile's Email box, never staff, never customers -- and a link is mailed only for an **active owner account**, to that recovery address. Text that is not shaped like a real email address (a username typed out of habit, a blank box) gets a plain red hint ("Please type a real email address, like name@gmail.com.", HTTP 400, what was typed is kept) instead of the false "on its way" message; that check says nothing about accounts. Limits (database-backed, `accounts.rate_limit`): 3 requests per email address and 10 per connection per hour. The sign-in, forgot-password and new-password pages show the Arabela logo centred above the heading (`templates/arabela_admin/partials/auth_logo.html`); the sign-in and forgot-password boxes carry their words only as placeholders (the old "Username*" / "Password*" labels above them are screen-reader-only now). Tests: `ForgotPasswordTests` and `SignInPagesLookTests` in `arabela_admin/test_owner_recovery.py`.
- **The link** (`/admin-panel/reset-password/<id>/<token>/`) opens a page that changes nothing until a new password is submitted (so a mail scanner that opens the link does not use it up). It works **once**, for **30 minutes**, and stops working when the password, the last sign-in or the recovery email changes. The new password follows the owner rules (10+ characters, not common, not only numbers, not close to the account details). Saving it signs out every device, lifts any sign-in lockout for that username, emails "your password was changed" to the recovery address, and sends her to the sign-in page. The page sends `Referrer-Policy: same-origin` (never `no-referrer`: that makes browsers post `Origin: null`, which Django's CSRF check refuses, so the password could not be saved -- found only in a real browser).
- **The emails** reuse the shop's one email design (`templates/emails/email.html`, `customer_emails.render_email`) and go out whether or not customer emails are switched on. The code email shows the code in a box; they are not in the Customer emails preview page.
- **Two doors that were open and are now closed.** (1) allauth's own `/accounts/password/...`, `/accounts/email/`, `/accounts/confirm-email/...` and `/accounts/reauthenticate/` pages were reachable: its "reset password" mailed a link to *any* account holding an address (owner, staff and customers) and accepted an 8-character password. Customers sign in with Google only, so those paths are now a plain 404 (`arabela_system/urls.py`); Google sign-in itself is untouched. (2) Django's built-in `/admin/` sign-in was a second place to guess the owner's password with no lockout; it is now a 404 too. The panel is `/admin-panel/`.

**If the owner cannot use the recovery email either** (never set one up, or lost that mailbox), whoever looks after the project resets it:

1. **Get the code:** `git clone` the GitHub repository and install `requirements.txt`.
2. **Recreate `.env`** (it is not on GitHub, on purpose). The database lines are also on Render → *Environment*: `DATABASE_HOST`, `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_NAME`, `DATABASE_PORT` (reveal each with the eye icon). Supabase → Project Settings → Database has the same details and can reset the database password. Without them the project quietly starts with an empty local database instead of the shop's.
3. **Reset the password:** `python manage.py changepassword <username>` and type the new password twice. If the username is forgotten too: `python manage.py shell -c "from django.contrib.auth import get_user_model as g; print(list(g().objects.filter(is_superuser=True).values_list('username', flat=True)))"`.
4. **Keep a private copy** of those five database lines (a password manager — never GitHub) in case Render and Supabase are ever out of reach.

Local development uses the **live** database, so step 3 changes the real password.

## 12. Category pictures

Every category has a picture on its tile on the customer site: the **Rentals** page, the **Women's** and **Men's** collection pages, and four tiles on the **home** page. Which picture a tile shows is decided in this order (`gowns/covers.py`):

1. the picture the owner uploaded in **Admin → Inventory Management → Categories** (owner only);
2. the picture that ships with the site, `static/images/categories/<category key>.jpg` — every original category;
3. the plain placeholder, `static/images/categories/placeholder.jpg` (the tile picture the site always had), for a category with neither: any category the owner adds, until they upload one.

- **Uploading (owner only):** choosing a photo shows the finished picture inside the category's card first (**Save** / **Cancel**); nothing is stored until Save. A photo must be a **tall photo of the whole gown on a plain white background**, **at least 400 × 650 px** (a note says a bigger one looks sharper below 600 × 900), JPG, PNG or WEBP, up to 5 MB. Each rule has one short message (`gowns/cover_images.py` → `prepare_cover`): not tall, too small, background not white, gown cut off at the edge, gown too small in the photo. The same rules run on the server for the preview and for Save, so they cannot be skipped. An accepted photo is turned into the exact tile picture: 600 × 900, the gown centred in the upper part, its white shaded to the tile grey (`#FBFBFB`), the strip at the bottom left free for the category name. The same code made the pictures that ship with the site, so uploads and bundled pictures look alike. (Checked against the shop's own 460 photos: 459 pass; the one that does not really is cut off.)
- **Viewing (owner only, same page):** each card with a picture has a **View** button next to Upload, and clicking the picture does the same. It opens a big view built like Payment Verification's "View Payment" window: the picture uncropped (never bigger than the file, sized so the whole view fits the screen), the category name strip as customers see it, which customer pages show it, whether it is **Standard**, **Custom** or a **Preview (not saved yet)**, its size in pixels, and a **View Full Image** link to the saved file (not shown for an unsaved preview). A chosen-but-unsaved photo can be viewed big before pressing Save. Closes with the x, Close, Esc or a click outside, and the keyboard focus goes back to the View button. A category with no picture (one the owner added) has no View button. It is all in `templates/arabela_admin/categories.html` (styles namespaced `.cvr-view-*`); there is no server code or database change.
- **Storing:** uploads go through the same storage as every other admin upload (Cloudinary on Render, the local `media/` folder otherwise) under `category_covers/`, and the name the storage gave each file is kept so replacing or resetting a picture deletes the old file. Removing a category the owner added removes its picture; removing one of the original categories keeps it, so adding that name back restores it.
- **Deploying:** this adds one table (`CategoryCover`, migration `gowns/0023_category_cover.py`). Run `python manage.py migrate` against the database **before** pushing to Render. If the code goes live first nothing breaks — customers just see the standard pictures, and the Categories page says uploads need the database update.
- **Renamed category:** *Ball Gown* is now **Evening Gown** (its address is `/collections/evening-gown/`; the old `/collections/ball-gown/` link and its product links still work). Two migrations carry the rename into the data — `gowns/0024` (gown category, ID prefix and `Ball Gown NN` names, number counters, Removal Log, removed-category list, tag colour, category picture) and `reservations/0023` (the gown name on existing bookings). Web addresses of individual gowns are unchanged, and *Ball Gown Tulle* is a separate category that was not touched. Deploy order for a rename like this: push, wait until Render is live, then run `python manage.py migrate` right away (the old site code would not find the renamed gowns).
- **Changing a picture that ships with the site:** `build_cover` and `cover_jpeg_bytes` in `gowns/cover_images.py` make the 600×900 JPEG from a photo; save it as `static/images/categories/<key>.jpg`. For a brand-new original category, also add its key to `BUNDLED_COVER_KEYS` in `gowns/covers.py`.

## 13. Backups and recovery

Supabase's free plan keeps **no backups** of the database, so the shop makes its own.

**Taking a backup** (read-only, safe any time, also against the live database):

```
python manage.py backup_database
```

It saves one compressed file, `arabela-backup-YYYYMMDD-HHMMSS.json.gz`, in `C:\Users\<you>\ArabelaBackups` (or the folder in the `ARABELA_BACKUP_DIR` setting, or `--output-dir`), reads the file back to prove it is complete, and keeps the newest 30 (`--keep N`). It holds every gown, reservation, customer, receipt, message and setting. It leaves out what `migrate` rebuilds (content types, permissions), current logins (sessions), the admin click log and failed-login counters. **The photos and payment proofs are not inside it**: they live in Cloudinary, which keeps them; the backup holds their addresses.

**Automatic daily backup (on the owner's laptop).** A Windows scheduled task named **Arabela Daily Backup** runs `C:\Users\<you>\ArabelaBackups\run-backup.bat` every day at **9 PM**, or the next time the laptop is on if it was off then. It saves into the Google Drive folder and keeps a short log in `C:\Users\<you>\ArabelaBackups\backup-log.txt` (the last line says `exit code 0` when it worked). The laptop must be on, signed in, and Google Drive for desktop running; if the Drive folder is not available the backup is saved in `C:\Users\<you>\ArabelaBackups` instead, with a warning in the log. Check it in *Task Scheduler → Task Scheduler Library*, run it now with `Start-ScheduledTask -TaskName "Arabela Daily Backup"`, and remove it with `Unregister-ScheduledTask -TaskName "Arabela Daily Backup" -Confirm:$false`. The task and its `.bat` file belong to that one laptop; they are not part of the project files.

**The file holds customers' personal details and password hashes. Keep it private**: never put it on GitHub (this repository is public), a shared drive or an email. Times are kept to the millisecond.

**If the database is lost** (a new, empty database is the only thing a restore goes into):

1. Create a new empty PostgreSQL database (for example a new free Supabase project).
2. Put its connection details in `.env` (`DATABASE_HOST`, `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_NAME`, `DATABASE_PORT`).
3. `python manage.py migrate`
4. `python manage.py restore_database C:\Users\<you>\ArabelaBackups\arabela-backup-....json.gz`

   It refuses a database that already has accounts, gowns or reservations (so it can never overwrite live data), clears what `migrate` pre-fills, loads the backup, and checks every table's count against the file. Customers are never emailed during a restore.
5. Point Render's `DATABASE_*` settings at the new database and redeploy.

The restore was tested on the real data: 484 records in 18 tables came back with every count, key and value matching. Run `backup_database` before any risky change (a big migration, a bulk delete) so there is always a fresh copy to go back to.

## 14. Error alerts and the uptime check

Two small safety nets, both free, so you hear about a problem before a customer has to tell you.

**The health page.** `/healthz/` answers `{"status": "ok", "error_alerts": "on" or "off"}` when the site is up and can reach its database, and `{"status": "error"}` (HTTP 503) when it cannot. It needs no login, shows nothing private, and asks the database one tiny question. A regular visit also stops Render's free plan from putting the site to sleep (the first visitor after a quiet period otherwise waits about 30 seconds).

**Uptime monitor (UptimeRobot, free):**

1. Sign up at uptimerobot.com, then **Add New Monitor** → type **HTTP(s)**.
2. URL: `https://arabela-gown-rental.onrender.com/healthz/`, check every **5 minutes**, and make sure your email is the alert contact.
3. Optional but good: in Render → the service → **Settings** → **Health Check Path** → `/healthz/`.

**Error alerts (Sentry, free):** when the live site crashes for a visitor, an email arrives with the exact page, line and code version.

1. Sign up at sentry.io (free plan), **Create Project** → platform **Django** → name it `arabela`. Copy the project's **DSN** (an address that starts with `https://`).
2. In **Render → the service → Environment**, add `SENTRY_DSN` with that address and save (Render redeploys). Do **not** put it in your laptop's `.env`: your laptop shares the live database, so its local errors would arrive as if they were the live site's.
3. Check it: open `/healthz/` on the live site; it should now say `"error_alerts": "on"`. To see an alert arrive, run on your computer: `$env:SENTRY_DSN = "the-address"; python manage.py send_test_alert` (PowerShell) and look in your Sentry inbox and email.
4. In Sentry, make sure email notifications are on for new issues (Alerts → the default rule, and your account's Notification settings).

What is sent is kept small on purpose (`arabela_system/monitoring.py`): the error, the page, and which version of the code was running. **No names, emails or IP addresses, and never what was typed into a form** (this was checked by sending a real crash to a stand-in Sentry and reading what arrived). Noise such as strangers' bots sending a made-up website name is dropped. Without `SENTRY_DSN` nothing is sent at all, so local development and the tests never report anything.

## 15. Page speed

The database is far from the web server (each question to it costs about 0.1 s), so speed comes from asking it fewer questions.

- **One page visit asks each category question once** (`gowns/request_memo.py`). The menu, the search box, the tiles and the page all read the category lists; they used to ask the database up to 15 times on one page. The memory lasts for that one visit only and is wiped the moment a category is added or removed, so nothing can ever show out-of-date categories.
- **The All page and Search fetch the gown list once** for every category (`_products_by_category` in `gowns/views.py`) instead of once per category, with the same filter, order and grouping as each category page.
- Measured on a copy of the real data (2026-10-10), every page byte-for-byte identical before and after: All page 45 → 5 database questions (4.7 s → 0.5 s), Search 49 → 9 (5.1 s → 0.9 s), category pages 11 → 5 (1.1 s → 0.5 s).
- **Static files are fingerprinted** (`arabela_system/storage.py`): `collectstatic` saves each file again with a short fingerprint in its name and pages point at that copy, which browsers keep for good (a changed file gets a new name, so nobody sees an old version). If a page ever names a file that does not exist it gets the plain name instead of crashing; a stylesheet pointing at a missing file stops `collectstatic` itself, so a broken build never goes live.
- **Gown photos are sent smaller** (`gowns/photos.py`): the customer pages ask Cloudinary for a resized, auto-compressed copy (800 px wide in the grids, 1600 px on the product and order pages, WebP where the browser supports it). Measured on the 29 live photos: 5.4 MB → 0.7 MB for the grids. The stored photo and the admin pages keep the original.
- The first visit after a quiet spell on Render's free plan still waits about 30 s while the server wakes; a paid instance, or a visit a few minutes before a demo, avoids that.

## 16. Error pages

`templates/404.html` (a page that does not exist) keeps the normal menu and footer and offers "Browse all gowns" (or "Back to the dashboard" inside the admin panel). `templates/500.html` (a crash) stands alone on purpose, with no database, no shared layout and its styles written inline, so it still appears when something is broken. Both only show on the live site: with `DEBUG=True` Django shows its own developer pages instead.

## 17. Laptop database (so local testing never changes the live shop)

Until this is set up, the laptop's `.env` points at the live database, and anything clicked locally really happens on the live site. To give the laptop its own copy:

1. In Supabase, create a second free project (same region as the live one), and keep its database password somewhere safe.
2. Copy `.env.laptop-db.example` to `.env.laptop-db` and fill it in from the new project's **Connect → Session pooler** page. The file is git-ignored and only its five `DATABASE_*` lines are read.
3. Build the tables and copy the live data across:
   ```
   python manage.py migrate
   python live.py backup_database
   python manage.py restore_database "<the backup file it printed>"
   ```

From then on `python manage.py runserver` says "Using the LAPTOP database" and the live shop is not touched. On the laptop, deleting a photo keeps the Cloudinary file (the live shop still shows it) and customer emails stay off.

To do something to the live database on purpose, use `live.py` for that one command: `python live.py migrate` after a new migration (run plain `python manage.py migrate` too, for the laptop copy). The daily backup task already runs `live.py backup_database`, and `backup_database` refuses to back up the laptop copy. Delete `.env.laptop-db` to go back to the old behaviour. Free Supabase projects pause after a week without use; press **Restore** in the dashboard to wake it.
